# 0002 루트 16px과 px 토큰

상태: 채택(잠정)   날짜: 2026-10-09   관련: D4, D12, D28, foundations §1·§3.2·§12-1, README §6-7

## 맥락

현재 앱은 `:root { font-size: 14px }` 위에 모든 토큰을 `rem`으로 적었다. 그래서 문서(`ui-visual.md`)가 "14/13/12, 48/36/28, 16/24 gutter, 896"이라고 말하는 모든 값이 화면에서는 **12.5% 작게** 렌더된다(`A-VIS-01`, P0). "문서의 숫자 = 화면의 숫자"가 깨져 있어 어떤 치수 검사도 문서를 믿을 수 없었다. 세 후보 모두 루트 16 + px를 택했다(judgment §2.4 D4).

웹에서 `rem`을 쓰는 이유는 브라우저의 기본 글자 크기 설정을 따르기 위한 것이다. 이 앱의 웹뷰(WKWebView·WebView2·WebKitGTK)에는 그런 사용자 설정이 없고, 글자 확대는 앱 안 설정(D28)이 맡는다.

## 결정

1. `html { font-size: 16px }`를 고정한다(앱·Worker 둘 다).
2. **모든 토큰은 px**다. `rem`·`em` 토큰은 없다. 행간도 **정수 px 토큰**(`--leading-body: 16px`)이다(foundations §12-1. brief §6.1-7의 "단위 없는 숫자"를 바꿨다: 의도인 `normal` 금지·결정적 값은 같고, px 토큰이 "문서 숫자 = 화면 숫자"와 생성기 검사에 더 맞는다).
3. 글자 확대는 `:root[data-text-scale="large|x-large"]`가 **글자·행간 토큰만** 재정의한다(×1.3/×2.0 [잠정]). 컨트롤 높이는 `min-height`라 따라 늘어난다. 크기 토큰(`--control-h` 등)은 글자와 분리되어 바뀌지 않는다.
4. 값 이름 토큰(`--space-8`)은 이름이 값이고 값을 바꾸지 않는다(foundations §1 규칙 2).

## 결과

- `design-tokens` T4(rem 0개, `html { font-size: 16px }` 존재), T5(행간 정수), T7(이름 = 값). `design-lint` L2(px 리터럴 금지는 토큰이 px이기 때문에 가능하다: 리터럴과 토큰이 같은 단위라 "토큰으로 바꾸라"가 늘 성립한다).
- 모든 기존 `rem` 선언이 바뀐다(단계 (a)·(b)·(c)).
- **Worker 읽기 페이지의 단점**: 브라우저 기본 글자 크기 설정(Chrome "글꼴 크기: 크게")이 px 글자에 적용되지 않는다. 브라우저 **줌**은 px에도 적용되므로 WCAG 1.4.4는 만족한다. 이 단점을 받아들이는 이유는 앱과 Worker가 같은 토큰 파일을 쓰기(D3) 때문이다. `web.md`가 이 한계를 적는다.

### 재검증 조건

- `data-text-scale="x-large"`에서 720×520 리플로우가 깨지면(갤러리 검사) 단계 값을 조정한다(토큰 블록만).
- Worker 읽기 페이지에 대해 "글자가 작다"는 문의가 2건 이상이면 reading 척도 값(foundations §3.3 [잠정])을 올린다. rem으로 되돌리지는 않는다.

## 대안과 버린 이유

| 대안 | 버린 이유 |
|---|---|
| 루트 16 + rem 토큰 | 웹뷰에 기본 글자 크기 설정이 없어 rem의 이점이 없고, 문서 숫자와 화면 숫자가 또 어긋날 길이 남는다(`A-VIS-01` 재발) |
| 루트 14 유지 + 문서를 화면에 맞춤 | 14 기준의 rem 값은 전부 소수(0.9286rem)가 되어 읽을 수 없다. 격자(4px)와도 맞지 않는다 |
| 행간을 단위 없는 비율로(brief §6.1-7 원안) | A 후보의 `1.2308` 같은 무리수가 생겼다(`J-F-A4`). 의도는 px 토큰으로도 만족한다 |
| 글자 확대를 `rem` 루트 변경으로(루트 16 → 21 → 32) | 크기 토큰·간격까지 같이 커져 720 창에서 레이아웃이 깨진다. 글자만 커지는 것이 D28의 뜻이다 |
