# 0005 대화상자 버튼 배치

상태: 채택(잠정)   날짜: 2026-10-09(편집 2026-10-10)   관련: D36, D35, P3, README §3-5, content §5.3, governance §3 R6

## 맥락

현재 앱의 대화상자 7종(취소 확인·창 닫기·로그아웃·업데이트·폴더 변경 등)은 버튼 순서·변형·기본 포커스가 서로 다르다(a-visual P0(4) 표, `A-VIS-05`·`A-VIS-26`). 세 후보는 두 갈래였다: A는 "오른쪽 끝 = 안전 = 채움 = Enter, 파괴는 왼쪽 빨간 글자", B·C는 "왼쪽 = 안전 + 기본 포커스, 오른쪽 = 파괴 테두리(채움 0개)". 근거만으로 갈리지 않아 사용자가 골랐다(`J-Q3`).

관련 외부 규칙: HIG alerts는 기본(default) 버튼을 trailing(오른쪽)에, 취소를 leading에 두라고 한다(`E-APPLE-22` confirmed). HIG buttons는 파괴 동작에 primary 스타일을 쓰지 말라고 한다. NN/g는 위험한 쪽을 기본(Enter)으로 두지 말라고 한다. 앱인토스는 왼쪽 닫기 관례(v-ko confirmed). Windows 대화상자 관례(확인 왼쪽)는 **[미확인]**이다.

## 결정

모든 대화상자에 규칙 하나를 적용한다(OS 분기 없음):

| 자리 | 내용 | 컴포넌트 |
|---|---|---|
| 오른쪽 끝 | **안전한 쪽** = 채움(`variant=primary`) = Enter = 기본 포커스. **안전 = 그 대화상자를 연 뒤 아무것도 하지 않은 것과 같은 결과**(현 상태 유지). 판정 기준은 이것 하나다 — "손실 없음"이나 "연 목적"은 기준이 아니다 | Button primary(Dialog `primary`) |
| 그 왼쇽 | 실행 쪽. 되돌릴 수 없으면 **빨간 글자 테두리 버튼**(`variant=secondary tone=danger`)을 버튼 줄 왼쪽 끝으로 띄우고, 되돌릴 수 있으면 회색 테두리 버튼(채움 옆) | Button secondary(Dialog `secondary`) |
| Esc | **닫기**(`onclose`). 어떤 버튼도 실행하지 않는다. 안전한 쪽이 현 상태 유지이므로 결과가 같다 | Dialog |
| 채움 버튼 수 | 포커스할 수 있는 층마다 정확히 하나 | — |
| 포커스 | 열릴 때 늘 오른쪽 버튼. 링은 `:focus-visible` 휴리스틱(포인터로 열면 안 보인다) | Dialog |
| 라벨 | 동사구. "취소"·"확인"·"돌아가기"·"닫기" 단독 금지. 안전한 쪽은 상태를 이어 가는 말(계속 받기·그대로 두기·나중에·로그인 유지). 7종 표는 `content.md` §5.3 | copy |

예(content §5.3): 받기 취소 [취소하고 지우기](빨간 글자, 왼쪽 끝) … [계속 받기](파랑 채움, Enter). 창 닫기 [일시정지하고 닫기] [계속 받기]. 로그아웃 [로그아웃] [로그인 유지] — 로그아웃은 되돌릴 수 있으므로 `tone=neutral`. 업데이트 [업데이트하고 다시 시작] [나중에]. 이전 설정 [가져오기] [나중에] — 가져오기는 상태를 바꾸므로 왼쪽이다.

HIG "취소 leading"과 충돌하는 유일한 경우는 **취소 확인 대화상자**다(안전한 쪽이 곧 "취소하지 않기"). 이 경우 안전한 쪽을 trailing에 두는 것을 예외로 명시한다. 그 밖의 대화상자에서는 "기본 = trailing"이 HIG와 같고, 어느 버튼이 기본인지는 HIG가 아니라 위 정의가 정한다(편집 전 초안의 "그 밖은 HIG와 같다"는 D5에서 [업데이트하고 다시 시작]이 기본이라는 반대 해석을 낳았다 — 검토 P0-1·U-02).

## 결과

- `components.md` §2.10 Dialog: 데이터 prop `primary`(오른쬭)·`secondary`(왼쪽, `tone`) 둘, 열리면 `primary`에 프로그램 포커스, `aria-describedby` 본문, Esc → `onclose`만.
- `content.md` §5.3: 7종의 제목·라벨 표(유일한 원천). `patterns.md` §5.2: 어느 상황에 어느 대화상자, 왼쪽 버튼 종류.
- `frontend` gate: Dialog 단위 테스트(`inert` 아닌 층에 채움 1개, 열리면 `document.activeElement` = 오른쪽, Enter가 오른쪽 핸들러, Esc는 `onclose`만, 포커스가 버튼이 아닐 때 Enter는 아무것도 실행하지 않음, `tone=danger`는 왼쪽 끝, 7종 표의 오른쪽 키 = 호출부 `primary`).
- `design-gallery`: 대화상자 7종 섹션에서 채움 버튼 수 = 1, 포커스 요소 = 마지막 버튼.
- 리뷰 `R6` 표(governance §3).
- e2e: `flow.spec.ts`·`settings.spec.ts`의 대화상자 단계가 버튼 라벨을 새 동사구로 참조(단계 (b)).
- `A-VIS-26`(마우스로 연 대화상자에 autofocus 링)은 `:focus-visible`로 해소된다(키보드 때만 링).
- Worker 확인 페이지(`web.md` §7.3)는 같은 좌우 규칙을 따르되 Enter 기본 버튼이 없어 오른쪽이 링크다.

### 재검증 조건

- D62 V2·V3(governance §6.4): 취소 대화상자에서 "오른쪽 파랑 = 안전"으로 읽는가, "왼쪽 빨간 글자 = 파괴"로 읽는가. **3명 중 2명 이상이 오른쪽을 "지우기"로 기대**하면 B·C 배치(왼쪽 안전 + 포커스, 오른쪽 파괴 테두리)로 뒤집는 ADR을 쓴다. 뒤집어도 Dialog 컴포넌트의 슬롯 순서만 바뀐다.
- Windows 실기에서 시스템 관례가 확인되고 Windows 참가자가 어긋남을 말하면 OS 분기(D2 예외) ADR.

## 대안과 버린 이유

| 대안 | 버린 이유 |
|---|---|
| B·C: 왼쪽 안전 + 기본 포커스, 오른쪽 파괴 테두리, 채움 0개 | HIG trailing 기본과 어긋나고, macOS 사용자(소영)에게 Enter가 왼쪽을 누르는 것이 낯설다. 채움 0개는 "채움 = 확정 지점 하나"(P3) 학습과 어긋난다. 실수 비용은 같다 |
| OS별 분기(Windows는 확인 왼쪽) | Windows 관례 [미확인]. 분기는 테스트 매트릭스를 두 배로 만든다(D2 "OS가 규정하는 값만 분기") |
| 파괴 쪽을 빨간 채움(`variant=primary tone=danger`) | HIG 파괴 primary 금지. 채움이 둘이 된다 |
| 취소 대화상자만 HIG대로 "취소 leading"(파괴가 trailing) | 규칙이 둘이 된다. 취소 확인에서 "취소"가 두 뜻(받기 취소·대화상자 취소)이라 라벨도 혼동된다 |
